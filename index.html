What it does

Haulers keep their data in separate systems: telematics in one, maintenance in another, billing and the general ledger somewhere else. The platform connects those sources, runs them through one pipeline, and puts the operating metrics an owner needs in one dashboard.

How it's engineered

  • Containerized services on a cloud server, with health checks and automated deploys that apply database changes before the new version starts.
  • Customer data kept in separate lanes by the database itself, with staff, client, and audited support access.
  • CI on every pull request: lint, type checks, unit tests, end-to-end browser tests, and a gate that blocks a database change until its production rollout is confirmed.
  • Secrets supplied at runtime, and production writes allowed only from the production server, so a rule people had to remember became one the system enforces.

Quality gates

For a data business, trust in the numbers is the product. Any bug class found twice becomes an automated gate, and gates cost nothing to run.

GateWhat it stops
Correctness gateRuns inside every refresh and blocks a bad or stale run before it reaches a client, with a named alert.
Golden-value gatesFourteen gates that lock audited figures to known-good values so corrected metrics cannot drift back.
Column gateFails CI when a dashboard tile reads a column that does not exist or that nothing fills.

Calls I made

  • Wrote the product spec and the metric definitions the pipeline is built to deliver.
  • Kept a standing set of rule files that tell the coding agents how to work in this codebase, so every session starts from the same conventions.
  • Re-planned the agent work by risk tier when the first sprint's cost told me the staffing model was wrong.

Cutting what the coding agents cost

A pilot on September 17 ran three lanes of very different size: a documentation edit, a mapping fix, and two new gates. Each cost 11 to 14 million tokens. What an agent spends is set by how much of the codebase it has to read and verify before it can act. So I re-planned the work by lane and staffed each lane by risk.

The first sprint also set the operating rules. It ran 13 hours against 3.5 planned: the account's usage limit paused every agent for about six hours, and merging 14 lanes took two integration trains. Now I check the remaining allowance before launch, cap the run at eight lanes, merge each on green, and stop to re-plan past 1.5 times the estimate.

  • Tier lanes by the files they touch. Tickets that share code share a lane.
  • Keep briefs under a page, trim test output, and hand off past about 150K tokens of context.
  • Next lever, about 45% of lane cost: cut what an agent reads before it acts, with a small-model scout that hands the builder the exact files.

The rule I set from the start: no black box. Every signal, allocator decision, and risk check is logged and viewable. A chat strategist sits on top with ten read-only tools (positions, exposure, pending plays, the explanation behind any play) and a brief to push back and never hype.

How I used AI to build it

  1. Wrote versioned specs (v9, v11, v12) with database schemas, API contracts, acceptance tests, explicit non-goals, and an execution order.
  2. Had an AI reviewer critique each spec, then pushed back wherever the critique cut something I cared about.
  3. Built with coding agents against a six-sprint plan: foundation, agents and allocator, playbook and mandate, chat, UI, polish.
  4. Brought screenshots of the running app back into a design review, since the reviewer could not see my local build.
  5. Got before and after mockups plus a file of exact directions for the coding agent, quick wins first.
  6. When small fixes piled up into clutter, called for a redesign from first principles.

Calls I made that the AI would not have

  • Caught that the v11 spec had dropped the chat strategist and mandate management from v9, and put them back.
  • Chose one coherent v12 release over splitting the scope into point releases.
  • Rejected a tabbed layout that hid detail and required a responsive grid that kept all of it.
  • Raised the minimum font size to 11 to 12 pixels after the AI defaulted to 8 or 9.
  • Required the agents screen to scale past 20 strategies, where the first draft showed 4 cards.
  • Asked for decision-first screens: fill probability, distance to market, and links to the originating play shown inline.

What it taught me

Context

An analysis session ran without my mandate in front of it. The spec now lives in the project, so every session starts with the full context.

Drift

The front end moved to the web while the spec still described a terminal UI. The spec now changes in the same pass as the build.

Defaults

The AI kept simplifying: tabs that hid detail, 8-pixel fonts, 4-card prototypes. I set the bar for density, scale, and readability up front.

Handoff

Design feedback in prose got lost on the way to the build. Mockups plus exact code directions became the standard handoff to the coding agent.

What I shipped

Bank sync over mutual TLS, transactions, budgets, payoff planning, credit and tax tracking, goals, a cash-flow schedule, forecast and subscription audit reports, and a command-line client. The in-app chat gets the live financial state in its context every turn, and has tools for a morning brief, a weekly review, and suggested savings cuts.

Three ways I used AI

  • Engineer. Coding agents wrote most of the app through feature branches and pull requests. I reviewed and merged. Four milestones shipped in about a week.
  • Product reviewer. I had an AI reviewer audit the half-built app the way a product manager would. It judged the app about 75% built and found the chat was acting as a bottleneck because there were no entry forms. My rule: make the call and explain why, and only ask me when my answer changes the outcome.
  • Analyst. AI analyst sessions read Bud's database directly with Python to build cash forecasts, scenario plans, and variance analysis against plan. A scheduled review runs twice a month, and persistent project memory lets each session pick up where the last one stopped.

What reconciliation taught me

An AI-run reconciliation checked Bud against the banks' own records. It surfaced three ways a synced finance app can look right and drift, and each one set a rule I now build to.

Dates

Balance dates. The feed stamped balances with its own sync time, so a stale balance read as current. Rule: carry the source's own timestamp all the way through.

Pending

Pending activity. Cash on hand read high with pending transactions left out. Rule: show what is in flight next to what has settled.

Gaps

Missing records. Some payments never arrived from the feed. Rule: count records against the source so gaps show up on their own.

None of these threw an error. They only showed up because the app was checked against the source of truth, and that check is now part of how I run anything that reports a number.

Work context server

DAILY USE

A local tool that records my working day, attributes it to the right project, and serves it to AI assistants through an MCP server I built, so they start from what actually happened.

Period
2026, in daily use
My role
Designer and builder
Built with
Agentic coding, Model Context Protocol
Runs
Locally on my Mac

What it does

  • Captures call transcripts and on-screen text, with full-text search across both.
  • Attributes time to each project using a project dictionary: names, match strings, attendee email domains, and a list of ways the transcriber mishears a name.
  • Gives AI assistants tools to pull a day or a date range, list meetings, read a transcript, list tasks, and search activity history.
  • Compresses older text into archives past a retention window, still searchable on request.

What it's for

The work I do produces a lot of context: calls, decisions, follow-ups across many projects running at once. The server lets me ask an AI assistant what was said on a call, where my week went, or what is open on a project, and get an answer from the record.

Across all four

How I work with AI

Spec first

Schemas, contracts, acceptance tests, and non-goals before any code. The coding agent builds to what I wrote down.

Set the bar

AI drifts toward simple. I decide density, scale, and readability, and I reject drafts that fall short.

Check against the source

Bank records for Bud, source systems for every implementation cutover I run at work. A plausible number is the dangerous one.

Keep context alive

Specs attached to projects, persistent memory, and the work context server, so each session starts from the real state of the work.

Redesign when patches pile up

Five sensible fixes can make a screen that has every piece and still does not flow. Start over when that happens.
